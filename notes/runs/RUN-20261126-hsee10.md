## Notes
Two `saarthi node serve` daemons from this tree (0.23.0) on rogue, against a hub of their
own on `127.0.0.1:7811`; the machine's own daemon (0.23.0 on `:7777`) kept running throughout
and was not touched. `run.log` is the run.

**A, default paths (H3).** Node x up: its wrapper socket and changes socket answer. Node y with
x's hook port exits on `Address already in use`, but only after it has deleted x's wrapper
socket and bound its own (the bind comes first in `serve`): x keeps running with no socket a
`saarthi run` can reach (inode changed, `dead`). With a hook port of its own, y runs: it takes
the wrapper socket over silently (`Wrappers::bind` removes what is there), and its changes
service refuses to start (`another server answers there (a second node?)`), so y's sessions'
changes are served by x. When y stops, the wrapper socket is left dead and x stays deaf to
wrappers. Both register with the hub as separate nodes.

**B, the user's Claude dir, every path given apart (H1, H2).** Both run cleanly. Each lists
every live session on the machine: 9 and 9, all 9 by both. Each uploads every one of those
sessions' transcripts from the start: about 114,700 events from each, the same ones, the
hub's database `locked` 3 times while it took them in (about 60 s). `~/.claude/settings.json`
names one hook URL, the machine's daemon on `:7777`. A session spawned on a (Haiku, one
prompt) is listed under a and, from b's registry scan, under b within 3 s, with two different
states (a: idle from its stream, b: busy from the registry). `ctl history` shows it twice.
Killing it on a ends it under both.

A first run of this version without the wait for the upload to settle
(`spawn-during-upload.log`): the spawn reached a, which started the session at once, but the
reply missed the hub's 15 s deadline while both nodes' uploads held its database. Before that,
two tries had other faults in the script (GNU `stat`; `nc -z` cannot probe a unix socket;
reusing one token across the parts) and are not kept.

The three spawned sessions (two Haiku replies of one word, one that timed out) ran in
`/tmp/s2n.*/work` under the machine's own login, so the machine's daemon reported them to the
owner's hub too, by its registry scan and the hooks in `settings.json`.

Ran before the spike was committed, on files identical to `commit` (8637e4a adds the scripts unchanged; `crates/` is the same at both).
