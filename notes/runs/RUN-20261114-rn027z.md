## Notes
The relay of ADR-0052 as a throwaway (`spikes/14-service-relay`, tonic and hyper, the
proto cut down to `Link`, `ServiceStream` and `ServiceRequest`), every piece on this laptop:
a hub, a node whose service `yajna` is a real `yajna serve` (0.30.1) on a scratch notebook
with a sparse 1 GB file, and the client as a loopback HTTP proxy, so the same requests go
straight to the service and through hub and node. Ten requests per kind; results in
`result.txt`.

| What | Direct, p50 | Relay, p50 | Same bytes |
|---|---|---|---|
| the files viewer `/files/` (1 KB) | 0.18 ms | 0.51 ms | yes |
| the site's index (1.7 KB) | 0.45 ms | 0.78 ms | yes |
| a listing | 0.18 ms | 0.54 ms | yes |
| 1 MB range at 512 MB (206) | 0.55 ms | 2.29 ms | yes |
| 256 MB range | 2 444 MB/s | 1 341 MB/s, first byte 1.4 ms | |

Server-sent events (`/api/events` watching a file appended to every second): all ten
changes arrived both ways, 263 ms after the write (yajna's own watching), the relay adding
0.2 ms at the median. With a 1 GB download running through the relay at the same time, all
five changes still arrived with 0.2 ms added (0.8 ms at most): each request is its own
HTTP/2 stream, nothing waits behind the download.

So H1 holds on one machine: no hop buffers, ranges and events pass whole and in order.
Not covered here: a real network between client, hub and node (the latency is then the
links', which ADR-0051's relay already crosses), and the node reaching the service over a
unix socket (the spike's node connects to `yajna serve`'s port, as `--socket` does not
exist yet; the node's code takes `unix:` too, untested).
