## Notes
Steps 2 to 4 of the plan, with the spike app in `spikes/15-libghostty-android/`:

- **libghostty-vt behind JNI.** `jni/vtjni.c` runs the command under a PTY (`forkpty`), as
  the node's shell would. A reader thread feeds the output to the terminal under a lock.
  Each display frame, if anything was fed, it copies the screen out of the render state
  into an int array: per cell the code point, resolved foreground and background, and
  style bits; plus the cursor and default colours. The copy uses the two-phase update, so
  the terminal is held only while it begins.
- **Linking.** `build-jni.sh` links `libghostty-vt.a` statically into `libvtjni.so`, with
  libc++ static for Highway's C++. The result is 2.1 MB and needs only `libc`, `libm`,
  `libdl` and `liblog`.
- **Drawing.** A Compose canvas draws the array in runs of one style: background rects,
  then `drawText` per run in a monospace font, with bold, italic, faint, underline,
  strikethrough and inverse.
- **The comparison.** Termux's `terminal-view` v0.118.0 from JitPack runs the same command
  under its own PTY, timed from a frame around its view, since `TerminalView` is final.
- **Loads:**
  - `yes`: 200,000 lines, 9 MB;
  - `log`: a file of 50,000 lines with 16, 256 and bold/faint colours, 4.9 MB;
  - `flood`: `yes` for ten seconds without end;
  - `top`: a full-screen redraw every half second.
- **What the spike measures:**
  - frames that changed and were drawn;
  - the copy (libghostty-vt only) and draw time, average and worst;
  - bytes fed;
  - the time until the command ended with all its output taken in.
- **Functional checks on the emulator.** Colours, bold, faint and inverse render right,
  and `top` lays out its screen. An interactive `sh` takes typed commands, and the key row
  sends Esc, Tab, Ctrl, the arrows and ^C.

**Emulator** (Android 15 `sdk_gphone64_arm64` on rogue, an M-series Mac; not a phone):

| `flood`, 10 s | 589 frames (59 fps), 184 MB taken in (18 MB/s), copy 0.11 ms, draw 0.31 ms (worst 2.6) | 1,112 updates; parses about 0.4 to 0.5 MB/s, so `yes` stalls on it |

An earlier pass gave the same picture: 183 ms and 349 ms for `yes` and `log` against
19.3 s and 11.7 s. Termux parses on the UI thread and redraws per update. libghostty-vt
parses on its own thread and draws at most once a frame, so a busy shell costs frames
nothing.

- **libghostty-vt keeps up with anything a shell sends.** It takes output in about 40 to 80
  times as fast as Termux's emulator. It drew every frame of a 10-second flood at 60 fps,
  and its worst frame (copy and draw together, 8.4 ms) still fits a 120 Hz frame (8.3 ms)
  nearly.
- **The 60 fps is the app's frame rate, not a limit of the library.** The spike asked for
  no higher rate, and a Samsung phone runs an app at 60 Hz unless it asks.
- **Termux's library would hold back a busy shell.** It parses on the UI thread,
  0.5 MB/s, so a `cargo build` or a `cat` of a log would wait on the phone.
- **What the run cannot control:** the phone's thermal state and background load; the
  emulator's numbers above are from rogue and only for comparison. The spike's sources are
  in the working tree at `commit`; they are committed with this run.

The spike was installed for this run and uninstalled after it. The phone was kept awake
over USB (`svc power stayon usb`) during the run, and the setting was turned off after it.
