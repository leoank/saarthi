## Notes
On the laptop (aarch64-darwin), step 1 of the plan: the build only; no device or emulator.

- **What was built.** Ghostty v1.4.0, the source and Zig dependency cache of nixpkgs'
  `ghostty` package at the project's nixpkgs rev (`ghostty.src`, `ghostty.deps`), with
  `zig_0_17` (0.17.1; `minimum_zig_version` is 0.17.0). The command:
  `zig build --system <deps> -Demit-lib-vt=true -Dapp-runtime=none -Demit-xcframework=false
  -Doptimize=ReleaseFast -Dtarget=aarch64-linux-android.26`, with `ANDROID_NDK_HOME` set
  to androidenv's NDK 30.0.16248370 (`spikes/15-libghostty-android/flake.nix`).
- **Android support is upstream.** The target needed no patch. Ghostty has a
  `pkg/android-ndk` build helper that finds the NDK from `ANDROID_NDK_HOME` and writes a
  libc file for the NDK's bionic sysroot, a workaround until Zig cross-compiles to bionic
  natively. lib-vt also sets 16 KB max page size for Android 15+.
- **Changes to the flake, not to Ghostty:**
  - The NDK comes from androidenv alone. The composed SDK also fetched the emulator.
  - The host control on macOS needs `cctools` for Apple `libtool`.
  - The host control on macOS also runs `/usr/bin/xcrun clang` from outside Nix to link
    the dylib. This is possible only because Nix's sandbox is off on Darwin, and the
    control is not pure.
- **The Android build in 4 min:**
  - `libghostty-vt.so` is 11.3 MB with debug info and 2.1 MB stripped;
    `libghostty-vt.a` is 22 MB.
  - It needs only `libc.so` and `libm.so`.
  - Its LOAD segments are aligned to 0x4000, the 16 KB pages Android 15+ requires.
  - It exports 211 `ghostty_*` functions, plus Highway's C++ SIMD symbols (`hwy::…`).
- **The smoke test** (`smoke.c`) writes `ls`-style coloured output, a cursor move, an
  erase and an absolute position into a 40×6 terminal, then reads the screen back as plain
  text through the formatter API:
  - On the host, the screen matches when linked against both the static and the shared
    library.
  - For Android, the same program links with the NDK's
    `aarch64-linux-android26-clang` against both the static and the shared library. It
    was not run, because there was no device in this step.
- **For the app's build:**
  - The shared library's soname is `libghostty-vt.so.0`. An APK installs only `lib*.so`
    files, so a JNI library that links against the shared one would not load. Link the
    static archive into the app's own `.so` instead (the Rust core or a JNI shim).
  - The `libghostty-vt-sys` crate (0.2.0 on crates.io) builds the same library from a
    pinned Ghostty commit. Its target map includes `aarch64-linux-android`, so the core
    could depend on it, with `GHOSTTY_SOURCE_DIR` pointing at this pinned source.
