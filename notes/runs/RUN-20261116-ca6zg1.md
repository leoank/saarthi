## Notes
The open question of [[RUN-20261115-2t8qqy]], whose link was slower than any cap: does
HTTP/2's flow control limit the relay over a long link, and does tonic's adaptive window
help? The owner asked for the adaptive window on 2026-11-16; this run was made first. The
link is simulated on this Mac by the spike's `delay` forwarder (43 ms each way between the
node and the hub and between the client and the hub, no bandwidth limit), the same requests
as [[RUN-20261115-2t8qqy]], once with tonic's defaults and once with
`http2_adaptive_window` on hub, node and client (`result-adaptive-0.txt`, `-1.txt`).

| | Default windows | Adaptive window |
|---|---|---|
| a small page | 271 ms | 271 ms |
| 1 MB range | 361 ms | 726 ms |
| 32 MB range | 9.8 MB/s | 7.4 MB/s |
| an event, idle / during a 128 MB download | +90 / +140 ms | +90 / +109 ms |

The window is not 64 KB: hyper opens a stream with 1 MB on the server's side and 2 MB on
the client's (`hyper-1.12.0`, `proto/h2/server.rs` and `client.rs`), so the defaults allow
about 10 MB/s per stream at 86 ms. Turning the adaptive window on resets both to 64 KB
(`SPEC_WINDOW_SIZE`) and grows them as it measures the link, so every short transfer
starts slow: the relay's traffic is mostly short (pages, ranges, Claude requests of 0.6 MB
at the median). The adaptive window is not adopted; if a faster or longer link ever needs
more, the fixed windows are raised instead.
